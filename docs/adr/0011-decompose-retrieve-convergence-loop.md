# 0007 — decision-navigator 分解⇄检索收敛循环

decision-navigator 不采用「检索一次 → 分解一次 → 评价」的线性流水线（原始设计稿 Phase 2→3 的顺序），而是分解与检索互为驱动的收敛循环：先从澄清后的请求拆出 strawman 子问题图；检索按开放节点的信息需求定向取材；检索成果反过来推进分解（新增 / 重开 / 解算节点）；循环至定点——某轮内零新增节点、零重开节点、零新增引用解算。线性方案被否：先检索后分解使检索失去靶向（不知该查什么），分解沦为事后审计而非规划器。硬上限 3 轮；达限时征询用户是否延长（轮数用户定，默认再 3 轮）——达限不按失败处理，余下开放节点按假设处理并在简报标注。

## Considered Options

- **线性「检索 → 分解」（原设计稿顺序）**：被否——检索无靶向；且与「分解驱动取材」的裁决（CONTEXT.md 决策分解）直接矛盾。
- **单轮 strawman + 修订权（初稿方案）**：被否——未知未知常需第二轮才浮出；相比收敛循环只是弱化版，且无显式收敛判据。

## Consequences

- 每轮先声明靶向（追逐的开放节点 + 信息需求）、后报变更（新增 / 重开 / 新增引用解算），「定点收敛」因此可审计；假设级变化不计为进展。
- 用户中途修正 = 节点重开 + 下游传播（可触发一轮小型定向重检索，或并入下一批澄清）；澄清批在轮界合并，每轮至多一批。
- 评价准则与排序在循环收敛后才进行——准则权重来自已解算节点。
- 子问题图在简报中双形呈现：mermaid flowchart（仅结构，SKILL.md 限定裸 `flowchart TD` 方言）+ 编号节点表（正典，含解算状态与「依：#n」引用）；evals 交叉校验两者（边一致、无环、节点覆盖）。
- 结构 evals 据此可断言：mermaid 可解析、边表一致、收敛声明在场、轮次不超上限（含用户批准的延长）。
